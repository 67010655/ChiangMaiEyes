## การตัดสินใจล่าสุดของผู้ใช้

- เพิ่มหน้าดู CCTV บนเว็บ โดยแสดงเวลาภาพ แหล่งกล้อง และสถานะการเชื่อมต่อ
- ไม่เชื่อม LINE ใช้ Resend ส่งอีเมลให้ผู้ลงทะเบียน ยืนยันอีเมล และเลือกเปิดรับ
- RECOFTC ให้เฉพาะขอบเขตป่าชุมชนจริงเชียงใหม่ 677 แห่ง ไม่ได้ให้ข้อมูลกิจกรรม เชื้อเพลิง กล้อง หรือเหตุการณ์
- มีต้นแบบกดใช้งานแยกจาก production ที่ `rebuild-preview/index.html` สำหรับทบทวนทุกหน้าหลัก ยังไม่มีการส่งอีเมลจริง
- ใช้ภาพ CCTV สาธารณะของ 5 สถานีแม่น้ำปิงจาก AppServ PingRiver ในต้นแบบแล้ว: P.1, P.67, P.75, P.92, P.20 แสดงที่มา เวลาในชื่อไฟล์ และเวลาตรวจรายการแยกกัน ภาพเป็น snapshot ไม่ใช่วิดีโอสด และยังไม่เชื่อมโยงว่าครอบคลุมป่าชุมชนใด

- ตรวจ source ใน checkout ปัจจุบันและเอกสาร production ของโครงการ ข้อสรุปเรื่องสูตร/ฟังก์ชันอ้างอิงโค้ดใน repo; ยังไม่ได้รับรอง deployment/config/RLS ของระบบออนไลน์ทั้งหมด
- หน้า production ตาม `docs/PRODUCTION_FRONTEND.md` คือ `frontend/index.html`; `frontend/src` ยังเป็นพื้นที่ทดลองและการย้ายระบบในอนาคต
- มี UX patch เดิมที่ยังไม่ commit ใน `frontend/index.html` ซึ่งลดแผงข้อมูลบางส่วน ข้อเสนอนี้ขยายเป็นการออกแบบโครงสร้างใหม่ทั้งประสบการณ์

## สิ่งที่เรียนรู้จากตัวอย่าง

### Coterie

ใช้พื้นสว่าง พื้นที่ว่าง ภาพถ่ายใหญ่ หัวข้ออ่านง่าย การ์ดขอบมน และการเปลี่ยนสถานะต่อเนื่อง เมื่อกดงาน ตัวเลขความคืบหน้าเปลี่ยนและ accordion เปิดเนื้อหาในบริบทเดิม หน้า mobile เรียงการ์ดลงมาได้

นำมาใช้: ความโปร่ง ความเป็นมิตร การประกอบหน้าเมื่อเปิดครั้งแรก ภาพในแต่ละการ์ด และ motion ที่ตอบสนองการกระทำ

ต้องออกแบบเพิ่มสำหรับเรา: ประโยคอธิบายข้อมูลภาษาไทย การเลือกพื้นที่ และความต่างระหว่างการตรวจพบจริง รายงานรอตรวจสอบ และภาพอธิบายหลักการ

### POPNIX Flood

เริ่มด้วยประโยคสรุปสถานการณ์ มีพื้นที่ของฉัน รายละเอียดจุดวัดแสดงภาพเทียบระดับกับเกณฑ์ แล้วจึงให้ดูกราฟ/ตาราง/แผนที่ ภาพ 3D มี legend อธิบายว่าความสูงและวัตถุแทนอะไร รวมทั้งระบุว่าวงน้ำเป็นภาพความรุนแรง ไม่ใช่ขอบเขตน้ำท่วมจริง ทัวร์ภูมิประเทศมีข้อความว่าความเร็วกล้องไม่ใช่ความเร็วของน้ำ

นำมาใช้: เริ่มจากความหมายของข้อมูล เลือกพื้นที่ง่าย ค่อยเปิดรายละเอียด ภาพเล่าเรื่องพร้อมคำอธิบาย และสถานะข้อมูลขาด/เก่า แบบเรียนสั้นช่วยผู้ใช้ตีความได้

ไม่ควรนำค่าระดับหรือสัญลักษณ์ของน้ำท่วมมาใช้แทนไฟป่าโดยตรง ต้องกำหนดความหมายให้ตรงกับข้อมูลไฟของเรา

อ้างอิง: [Coterie preview](https://demo.codeandchill.store/coterie/), [POPNIX Flood](https://flood.pop.in.th/), [3D](https://flood.pop.in.th/3d/?v=th)

## ประสบการณ์ใหม่ที่เสนอ

### 1. หน้าสาธารณะ — เข้าแล้วอ่านสถานการณ์ได้

1. Header สั้น: สถานการณ์วันนี้ / พื้นที่ของฉัน / เข้าใจไฟและควัน / สำหรับชุมชนและเจ้าหน้าที่
2. พื้นที่แรกเป็นฉากภูเขาและป่าของเชียงใหม่ที่มี motion อ่อน พร้อมประโยคสรุปจากข้อมูล เช่น “พบจุดความร้อนในข้อมูลล่าสุด” ระบุพื้นที่และช่วงเวลา ข้อความตัวอย่างต้องไม่ใช้เป็นสถานการณ์จริง
3. ตัวเลือกพื้นที่โดยพิมพ์ชื่ออำเภอ ตำบล หรือป่าชุมชน ใช้งานได้โดยไม่เปิดตำแหน่ง ไม่บังคับ login
4. การ์ดภาพ 3 เรื่อง: จุดความร้อน / ฝุ่นใกล้พื้นที่ / ลม แต่ละการ์ดมีภาพ ค่าหลัก ประโยคแปลความหมาย และเวลาตรวจวัดหรือเวลาภาพ
5. แผนที่อ่านง่าย เปิดเฉพาะชั้นที่จำเป็น แตะจุดแล้วเปิดรายละเอียดพร้อมแหล่งข้อมูลและสถานะการตรวจสอบ
6. “อะไรเปลี่ยนไป” ใช้ข้อมูลย้อนหลังจริง เปรียบเทียบช่วงที่มีข้อมูลและใช้แหล่ง/ขอบเขตที่เทียบกันได้
7. ส่วนภาพเล่าเรื่อง: ดาวเทียมเห็นอะไร / ลมพัดจากไหนไปไหน / เหตุใดไม่มีจุดตรวจพบจึงยังสรุปว่าปลอดภัยไม่ได้
8. ปุ่มเปิดงานชุมชนและเจ้าหน้าที่ที่เห็นชัด สถานะ loading, ไม่มีข้อมูล, ข้อมูลเก่า, offline ต้องแสดงความหมายต่างกัน

ให้แผนที่ 3D เป็นประสบการณ์ที่เปิดเพิ่มได้ ส่วนอ่านสถานการณ์พื้นฐานต้องใช้ได้บนโทรศัพท์และเครือข่ายช้า

### 2. พื้นที่ทำงานชุมชน — ข้อมูลที่เกี่ยวกับพื้นที่ดูแล

- เลือกป่าที่รับผิดชอบ/พื้นที่นำร่องแล้วแสดงจุดที่เกี่ยวข้อง รวมจุดใกล้เคียงนอกขอบเขต พร้อมแยกผู้รับผิดชอบและหน่วยที่ประสาน
- รายงานพบควัน/ไฟ พร้อมตำแหน่ง เวลา และหลักฐานที่ผู้ใช้มี กระบวนการยืนยันเป็นอีกสถานะหนึ่ง
- ลำดับเหตุการณ์: พบเหตุ → ตรวจสอบ → รับเรื่อง/ประสาน → อัปเดตสถานการณ์ → ยืนยันปิดเหตุโดยผู้มีหน้าที่ → บันทึกบทเรียน
- มีผู้บันทึก เวลา และหลักฐานทุกการเปลี่ยนสถานะ ต้องกำหนดบทบาทจริงก่อนให้สิทธิ์แก้ไข
- เริ่มจากข้อมูลและช่องทางที่ชุมชนใช้อยู่ ใช้ Resend ส่งอีเมลหลังยืนยันบัญชีและการเปิดรับ ตามการตัดสินใจล่าสุดของผู้ใช้
- การใช้ระบบสนับสนุนเฝ้าระวังและประสานงาน ไม่ถือว่าการกดปุ่มในเว็บเป็นการอนุมัติเผาหรืออนุญาตใช้ไฟโดยอัตโนมัติ

### 3. พื้นที่เจ้าหน้าที่ — เครื่องมือและหลักฐานละเอียด

- ภาพรวมจังหวัด, พื้นที่รับผิดชอบ, พื้นที่นำร่อง, ข้อมูลรายจุด/ชุมชน, ช่วงเวลา, ตาราง, export และแผนที่ 2D/3D
- แหล่งข้อมูล เวลาอ้างอิง ความละเอียดข้อมูล สูตรและข้อจำกัดอยู่ใกล้ข้อมูลที่เกี่ยวข้อง
- เก็บเครื่องมือเดิมผ่านรายการตรวจความครบถ้วนของ feature ก่อนย้าย entry หรือแทนหน้าปัจจุบัน
- ซ่อนข้อมูลละเอียดหลังปุ่มเป็นการจัด UX; ข้อมูลที่มีสิทธิ์จำกัดต้องควบคุมที่ API/ฐานข้อมูลด้วย

## ภาพและ motion

โทนหลัก: white #FFFFFF, soft white #F6FAF7, forest green #0F6B54, leaf green #16A34A, ink #10231D สีเตือนใช้ amber/orange/red พร้อมข้อความและสัญลักษณ์ตามความหมาย

ใช้ภาพป่า/ชุมชน/หน้างานที่มีสิทธิ์ใช้งาน และภาพวาดภูเขา ป่า หมู่บ้าน ดาวเทียม กล้อง โดรนและลมให้มีชุดภาษาภาพเดียวกัน

| ส่วน | Motion ที่เสนอ | สิ่งที่ต้องสื่อและข้อจำกัด |
| --- | --- | --- |
| เปิดหน้า | ฉากและหัวข้อค่อยปรากฏ พร้อมการ์ดเข้าทีละกลุ่ม | ไม่รอ animation จบจึงอ่านข้อมูลได้ |
| ฉากธรรมชาติ | ใบไม้/แสง/เมฆขยับเบา | ภาพประกอบ ไม่อ้างว่าเป็นสภาพจริงทั้งจังหวัด |
| จุดความร้อน | เน้นจุดที่เลือกหรือจุดใหม่อย่างสั้น | จุดตรวจพบ ไม่ใช่ขอบเขตไฟหรือไฟกำลังลุกทุกจุด |
| PM | มาตรวัดและภาพอธิบายค่อยเปลี่ยนเมื่อข้อมูลเปลี่ยน | ใช้ค่าจุดวัด ระบุชนิด sensor และเวลา ไม่สร้างค่าฝุ่นระหว่างค่าจริง |
| ลม | ลูกศร/เส้นเคลื่อนไปตามทิศที่กำหนด | มี FROM/TO ความสูง เวลา แหล่งข้อมูล ไม่เรียกว่าเส้นทางไฟหรือควันที่พิสูจน์แล้ว |
| เปลี่ยนพื้นที่ | transition เชื่อมชื่อพื้นที่ การ์ด และแผนที่ | ระหว่างโหลดต้องไม่ค้างค่าพื้นที่เก่าโดยไม่มีป้าย |
| กราฟย้อนหลัง | วาดกราฟและเล่นตามเวลาที่มีข้อมูล | ไม่มีข้อมูลต้องเห็นช่องว่าง ไม่ interpolation เป็นเหตุจริง |
| รายละเอียด | expand, drawer/bottom sheet, highlight จุด | เปิดในบริบทเดิม ปิดและกลับด้วย keyboard ได้ |
| งานชุมชน | เปลี่ยนสถานะและตอบรับการบันทึก | แสดงสำเร็จหลัง server รับข้อมูลแล้ว |
| ส่วนเรียนรู้ | ฉากอธิบายเป็นขั้นและตัวควบคุมเล่น/หยุด | แยกภาพหลักการออกจากข้อมูลตรวจวัด |
| ปุ่ม/เมนู/filter | hover/focus/press, indicator เคลื่อน | ทุก interactive component มี feedback ที่สม่ำเสมอ |
| โหลด/ผิดพลาด | loading สั้น, transition ไปสู่คำอธิบาย | ข้อมูลหายไม่ใช้ animation “ปลอดภัย” |

ทุกส่วนมีพฤติกรรม motion ที่กำหนด แต่ไม่ต้องเคลื่อนไหวตลอดเวลา ให้ผู้ใช้หยุดภาพหลักได้ รองรับ reduced motion โดยคงข้อมูลครบ ลดการทำงานเมื่ออยู่นอกจอ/แท็บเบื้องหลัง และมีโหมดเบาสำหรับเครื่องหรือเน็ตช้า

## Graphify ในงานนี้

มีประโยชน์เป็นเครื่องมือช่วยทำแผนที่ dependency ก่อน refactor และตรวจเส้นทาง UI → API → provider/ฐานข้อมูล ข้อเสนอให้ทดลองกับเส้นทางที่รู้จริง 3 เส้น: dashboard, community forests, manual reports แล้วตรวจ graph กับ source

README แยก AST code ที่ทำ local ออกจากเอกสาร/ภาพ/PDF ที่ใช้ semantic model ตาม backend ที่เลือก จึงไม่ควรเหมารวมว่าการใช้ทั้งหมดไม่มีข้อมูลออก cloud `.html` ถูกจัดเป็น Docs; ยังไม่ทดสอบว่าจะอ่าน inline JavaScript ใน production ของเราครบ ผล inferred ต้องตรวจต้นทาง เครื่องมือไม่ได้แทน parity test, live API verification หรือ usability test รอบนี้ตรวจเอกสาร ยังไม่ได้ติดตั้ง/benchmark กับ repo นี้

อ้างอิง: [Graphify official repo](https://github.com/Graphify-Labs/graphify)

## ลำดับทำงานและ deploy

1. **ยืนยันข้อมูลและทำทะเบียน feature**: เก็บรายการเครื่องมือเดิม/เส้นทางใช้งาน/แหล่งข้อมูล; แก้ป้ายผิดและ freshness; จัดรายการ review → requirement → acceptance
2. **ทำต้นแบบประสบการณ์ใหม่**: public desktop/mobile, ฉากและ motion จริง, จุดรายละเอียด, empty/stale/offline states และทางเข้าชุมชน/เจ้าหน้าที่ ใช้ dataset fixture ติดป้ายตัวอย่างชัดก่อนต่อข้อมูลจริง
3. **Preview ที่ต่อข้อมูลจริง**: ย้าย public surface โดยเก็บเครื่องมือเจ้าหน้าที่ครบ ตรวจ 2D/3D, เลือกพื้นที่, filters, report/login/history/delete, PDF/CSV, เวลา และ fallback
4. **ทดสอบ 1–2 ชุมชนและ admin**: ให้ผู้ใช้เลือกพื้นที่ บอกสถานการณ์ บอกเวลาข้อมูล เปิดจุดและอธิบายว่ายืนยันแล้วหรือยัง; วัดความเข้าใจ เวลาและข้อผิดพลาด
5. **เปิด production ทีละชุดที่ใช้งานจบ**: รุ่น public ใหม่+ข้อมูลเชื่อถือได้; รุ่น incident/community workflow; รุ่น CCTV/Resend/ข้อมูลวิเคราะห์ที่ผ่านการประเมินแล้ว

แต่ละรุ่นต้องมี preview, การเทียบ feature เดิม, แผน rollback และตรวจหน้า deployed พร้อม API หลังปล่อย ไม่รอทุก feature research เสร็จพร้อมกัน แต่ไม่ปล่อย UX ครึ่งเส้นทางที่ทำให้ข้อมูลหรือเครื่องมือเดิมหาย

## เกณฑ์ตรวจรับที่เสนอ

- ผู้ใช้ทั่วไปตอบได้ว่าพื้นที่ไหน ข้อมูลช่วงไหน พบอะไร และอะไรยังไม่ยืนยัน โดยไม่ต้องอ่านสูตร
- ตั้งเป้าทดสอบการอ่านสถานการณ์ใน 10 วินาทีเป็นเป้าหมายออกแบบ ไม่ใช่ผลที่วัดได้แล้ว
- หน้าแรกไม่บังคับ login/location; เจ้าหน้าที่กลับเข้าเครื่องมือเดิมได้ครบ
- mobile 360/390/768 px และ desktop ใช้ได้ ไม่เกิด horizontal overflow; ปุ่มแตะและข้อความไทยอ่านสะดวก
- เปิด reduced motion แล้วยังอ่านข้อมูลครบ; หยุดฉากเคลื่อนไหวได้; ไม่บังคับใช้ WebGL เพื่อดูสถานการณ์พื้นฐาน
- satellite/manual/camera และสถานะยืนยันมีคำ/สัญลักษณ์ต่างกัน; unknown ไม่กลายเป็น green/safe
- การสลับเวลา/พื้นที่ไม่แสดงตัวเลขค้างในบริบทใหม่; timestamp และ source สอดคล้องทุกจุด
- data replay ใช้ observation จริงตามเวลา ไม่สร้างการเคลื่อนที่ของไฟระหว่างจุดที่ไม่มีหลักฐาน
- permission ของรายงาน/พื้นที่จำกัดตรวจจาก API/RLS จริงก่อนเปิด; ไม่ใช้ปุ่มซ่อนข้อมูลแทนการจำกัดสิทธิ์
- build และ meaningful parity checks ผ่าน ตรวจ live API และ preview browser ด้วย; ข้อผิดพลาดเดิมต้องรายงานโดยไม่กล่าวว่าระบบ clean ถ้ายังเหลือ

## ข้อมูลที่ต้องได้จากผู้ใช้/หน่วยงานก่อนทำส่วนที่เกี่ยวข้อง

1. รายชื่อป่านำร่อง 8 แห่ง ชุมชนเริ่มทดสอบ 1–2 แห่ง และตำบลนำร่องที่สะกดถูกต้อง
2. กลุ่มผู้ใช้/หน่วยที่มีสิทธิ์ตรวจสอบ รับเรื่อง เปลี่ยนสถานะ และยืนยันปิดเหตุ
3. ข้อตกลงหรือคำยืนยันเรื่องการเผยแพร่ขอบเขต/ชื่อ/ข้อมูลจาก RECOFTC
4. กล้องที่อนุญาตให้ใช้ จุดติดตั้ง เจ้าของข้อมูล API/ภาพที่เข้าถึงได้ และข้อจำกัด
5. แหล่งกล้อง URL/รูปแบบภาพ เจ้าของและสิทธิ์เข้าถึง; sender domain และการตั้งค่า Resend สำหรับส่งจริง

รายการนี้ไม่ขวางการทำต้นแบบ public UX แต่ต้องได้คำตอบก่อนสมมติการเชื่อมระบบภายนอกหรือสิทธิ์การทำงาน
