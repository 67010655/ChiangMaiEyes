# Open-source improvements that do not require a field campaign

Checked 2026-10-17. Scope: practical upgrades for ChiangMaiEyes, with primary documentation and source code. These are candidate improvements; no accuracy gain is assumed before testing.

## What the repository already does

`backend/app/live_spread.py` uses an FM1 reference fuel, moisture fixed at 8%, and a 0.2 wind adjustment factor. Its hourly inputs are wind only. `backend/app/grid_spread.py` propagates over the existing approximately 110 m terrain grid and uses WorldCover 2021 to block selected cover classes. It still imports that same fuel and wind factor. Thus terrain, a grid solver, and static land cover are **already implemented**; repeating them is not a new improvement. The downloaded weekly burn scars are verification evidence, not the preceding-hour vegetation/fuel state.

## Highest-value next experiments

1. **Learn next-observation risk from the complete hotspot history.** Predict subsequent independent detections using earlier spatial intensity, elapsed time, FRP/confidence, terrain, and land cover. Add preceding weather and vegetation only when their availability times are known. Evaluate ranking and calibration, and compare against recency/distance baselines at the same alert area. This changes the immediate dashboard product to a useful probability/ranking question that the available labels can actually test. It does not turn detections into verified fire perimeters. This experiment is an engineering recommendation, not a claim from a source.
2. **Replace fixed fuel moisture with weather-conditioned state.** NASA/NOAA/open weather provide temperature, humidity, rain, and solar variables; estimate moisture over a preceding conditioning period and forecast it forward. The USFS Nelson implementation accepts elapsed time, air temperature, humidity, solar radiation, and rainfall. NWCG describes hourly moisture conditioning in spatial growth models. Distinguish a weather-derived estimate from direct measured moisture, and preserve uncertainty/initial-state sensitivity. Test constant 8% versus conditioned state with identical origins, wind, and scoring. [USFS source](https://github.com/firelab/NFDRS4/blob/master/lib/NFDRS4/src/deadfuelmoisture.cpp), [NWCG guidance](https://www.nwcg.gov/publications/pms437/fuel-moisture/dead-fuel-moisture-content).
3. **Treat the initial fire state as a pixel observation, not a point ignition.** VIIRS locations mark pixel centers; scan/track describe actual pixel size. Reconstruct a footprint or sample possible subpixel origins, then propagate from acquisition to issue time before forecasting. Global FIRMS latency is within three hours; acquisition UTC does not equal receipt time. Group the three satellites' roughly one-hour observation cluster when constructing independent prediction targets. Score a declared 0/1/3-hour latency sensitivity rather than assuming instantaneous receipt. The entire pixel need not be burning; a footprint ensemble represents uncertainty. [NASA FIRMS fields and timing](https://firms.modaps.eosdis.nasa.gov/content/descriptions/FIRMS_VIIRS_Firehotspots.html).
4. **Use appropriate multi-class reference fuels and variable canopy shelter.** FM9 is hardwood litter and requires 1-hour, 10-hour, and 100-hour dead fuel moistures. It cannot be represented faithfully by changing a few constants inside the present single-dead-class routine. Compare FM1, FM9, and suitable litter/grass alternatives through an established multi-class implementation. Treat vegetation-to-fuel assignments as hypotheses, not measured Thai fuel classifications. [Federal IFTDSS moisture requirements](https://iftdss.firenet.gov/firenetHelp/help/pageHelp/content/00-concepts/fbfm/fbfmfuelmoistures.htm).

## Open data that can improve inputs now

| Data | Concrete new use | Availability and limits |
|---|---|---|
| Sentinel-2 Level-2A | Pre-issue cloud-masked NDVI, NDMI, NBR; seasonal change, recent clearing/burns; update stale cover | Public Earth Search STAC indexes Sentinel imagery with COG assets. A live unauthenticated query for Chiang Mai returned Jan–Apr 2026 items, including red/NIR/SWIR/SCL assets. Tile cloud percentage does not prove local clear pixels. NDMI is a canopy-water proxy, not calibrated litter moisture. [Provider README](https://github.com/Element84/earth-search/blob/main/README.md), [Copernicus L2A specification](https://documentation.dataspace.copernicus.eu/APIs/SentinelHub/Data/S2L2A.html). |
| GEDI canopy structure | Canopy height/cover priors for shelter and a plausible wind-adjustment ensemble | Products provide footprint-based canopy metrics; biomass is model-derived. Sparse footprints or spatially inferred maps are not continuous current fuel-bed measurements. [GEDI product owner](https://gedi.umd.edu/dataproducts/products/). |
| Himawari-9 AHI | More frequent evidence of active fire growth and smoke than polar overpasses alone; reinitialize when detections arrive | JMA full-disk observations are every 10 minutes. Public NOAA/JMA imagery is listed on AWS. Turning imagery into reliable fire detections needs an actual detector and cloud handling; cadence alone does not give 10-minute accuracy or 375 m resolution. Use it as a new observation stream with its own uncertainty. [JMA cadence](https://www.data.jma.go.jp/mscweb/en/himawari89/himawari_cast/himawari_cast.php), [Open-data access](https://registry.opendata.aws/noaa-himawari/). |

## Existing open-source solvers: what they actually add

| Tool | Practical fit | Inputs and integration work |
|---|---|---|
| **Pyrothermel / Behave** | Fastest way to replace the hand-built single-class spread-rate calculation with a multi-class reference calculation | Python bindings around C++ Behave; documented build testing includes Visual Studio 2022 and WSL gcc. Supports fuel model, moisture scenario, slope/wind inputs, canopy variables, and ten-meter wind adjustment. It computes fire behavior; the existing grid solver would still provide spatial propagation. Pin versions and verify units with controlled cases. [Owner's code/docs](https://github.com/j-tenny/pyrothermel). |
| **Pyretechnics** | Most direct scriptable alternative for array-driven spatial spread experiments | Provides surface/crown/spot-fire modules and a level-set spread algorithm; space-time cubes unify fuel, terrain, wind, and moisture arrays. Can ingest existing aligned rasters and output arrival/intensity arrays. Current project declares Python 3.11-compatible requirements and NumPy/SciPy/rasterio/Cython dependencies. CPU/library/build compatibility must be checked in an isolated environment before adopting in the serverless backend. [Owner README](https://github.com/pyregence/pyretechnics), [Build requirements](https://github.com/pyregence/pyretechnics/blob/main/pyproject.toml). |
| **ELMFIRE** | Strong offline benchmark and potential ensemble worker | Linux/WSL build using Fortran/MPI/GDAL. Requires terrain, fuel models, initial fire state, canopy parameters, transient wind and several moisture classes; GeoTIFF inputs must align with documented units. Supports stacked time-varying weather rasters. Existing Chiang Mai terrain/cover help, but a WorldCover class is not the required fuel model raster. Run explicit own inputs; do not assume US-oriented tutorial fuel services cover Thailand. [Official computational guide](https://elmfire.io/user_guide.html). |
| **WindNinja** | Terrain-adjusted wind, a genuinely new input beyond per-origin coarse GFS | Diagnostic wind model with Windows and Linux paths. Use a local DEM and domain-average or supported weather initialization; produce spatial speed/direction rasters for the fire solver. Validate behavior on a small domain first. It provides local wind structure, not automatic proof of improved spread skill. Source build has substantial GDAL/NetCDF/Qt/Boost dependencies. [USFS overview](https://research.fs.usda.gov/firelab/products/dataandtools/windninja), [USFS code](https://github.com/firelab/windninja). |
| **FARSITE** | Useful reference, less convenient as the first new runtime in this project | USFS explicitly says FARSITE4 is unsupported/unavailable and FARSITE is now included in FlamMap6. Older community Linux ports are different distributions. A random GitHub fork should not be described as the current official maintained release. It still needs landscape/fuel/moisture/weather and initial fire geometry. Prefer the documented Python or ELMFIRE route first unless an exact FARSITE benchmark is required. [USFS tool](https://research.fs.usda.gov/firelab/products/dataandtools/farsite), [Community-port ownership warning](https://github.com/mbedward/farsite/). |

## Experiment and release criteria

- Freeze the target: independent later detections for surveillance prioritization; time-resolved verified perimeters for physical spread. Weekly final burn scars cannot identify a six-hour fire perimeter.
- Fit on earlier dates, select on a later validation block, and evaluate on the final chronological block. Existing April data have already been inspected in earlier experiments: describe a new split as retrospective validation, not a previously untouched independent confirmation.
- Ablate changes: static moisture; dynamic moisture only; multi-class fuels only; revised initialization only; then their combination. Same inputs, same dates, same latency assumptions, same area budget.
- Report coverage **and** alert area, precision/false alerts where observable, probability calibration, and results by date/region. Satellite non-detection alone is not proof of no fire; report missing/cloud/overpass uncertainty.
- Archive issued forecasts and compare new observations prospectively. Promote only improvements supported by the intended task; keep unproven physical scenarios labeled as scenarios.

**Recommended order:** complete full-history statistical risk experiment now; add preceding weather-conditioned moisture and pixel-state initialization next; evaluate a pinned Pyrothermel/Pyretechnics benchmark; then terrain-adjusted WindNinja. None of these requires making a field visit a prerequisite. Actual local measurements remain useful later for tightening uncertainty, rather than blocking all progress today.

## Executed follow-up

The full-history statistical experiment has now completed: 2024 training, 2025 selection, 2026 retrospective test, with a separately tuned 18-configuration neighbour baseline. At 250 km2 per issue, detection-cell coverage is 35.0% versus 28.4%; see `output/priority-forecast-20261017/RESULTS.md`. This is a surveillance-ranking result, not fire-perimeter accuracy. The production dashboard presents historical replay and does not run this model as a live forecast.

The pinned Pyretechnics pure-Python surface-rate path and a WRFx weather-driven 1/10/100-hour moisture calculation were also executed. They did not establish a directional-spread advantage over matched-area buffers. See `output/open-fuels-pilot-20261017/summary.json`.

It should therefore be described as source-available under its own terms, not assumed to be an unrestricted OSI open-source dependency.
