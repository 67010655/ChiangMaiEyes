# Satellites on Fire: ตรวจสอบต้นทางและประโยชน์ต่อ ChiangMaiEyes

ตรวจสอบวันที่ 18 ตุลาคม 2026 จากแหล่งเจ้าของระบบ ผู้จัด Earthshot และเอกสารหน่วยงานดาวเทียม รวมถึงเปิดเว็บแอปจริงแบบไม่ลงทะเบียน ไม่ส่งข้อมูลติดต่อ และไม่สมัครบริการ ภาพที่ผู้ใช้ส่งหมายเลข 1, 2 และ 7 เป็นโครงการเดียวกัน ส่วนความเห็นในภาพ 7 เป็นการแนะนำแหล่งข้อมูล ไม่ใช่ผลทดสอบความแม่นยำ

## ข้อสรุปที่ใช้ตัดสินใจได้

**เหมาะนำแนวทางตรวจพบเร็ว → ตรวจสอบหลักฐาน → แจ้งคนที่รับผิดชอบ → บันทึกผลตอบรับมาพัฒนาระบบเราอย่างมาก แต่ยังไม่มีหลักฐานให้เลือกเป็นโมเดลไฟลามที่ดีกว่าโมเดลของเรา หรือดึง API มาใช้ในเว็บเชียงใหม่ได้ทันที**

สิ่งสำคัญที่สุดที่ตรวจพบจากการเปิดแอปจริงคือ แอปแสดงข้อความว่าขณะนี้ยังไม่แสดง detection ของประเทศไทยบนแผนที่สาธารณะ และเสนอให้ฝากข้อมูลติดต่อเพื่อหารือการติดตามพื้นที่ ข้อความนี้แยกชัดระหว่าง “เปิดแผนที่โลกได้” กับ “มีข้อมูลที่ให้บริการในเชียงใหม่จริง” บริษัทระบุว่าสามารถครอบคลุมพื้นที่ได้ แต่ยังไม่ได้รับรองดาวเทียม ผลิตภัณฑ์ ความถี่ ความหน่วง หรือบริการที่เปิดให้ไทย ([เว็บแอป](https://app.satellitesonfire.com/))

## 1. โครงการคืออะไรและทำอะไรจริงตามเอกสาร

เป็นแพลตฟอร์มเชิงพาณิชย์สำหรับตรวจพบไฟและจัดการการแจ้งเตือน มีแผนที่ hotspot และประวัติ พร้อมบริการภาพกล้อง/สภาพอากาศ การติดตามเหตุ และการจำลองไฟลาม เว็บไซต์ระบุการติดตามดาวเทียมทุก 10 นาที **สำหรับทวีปอเมริกา** การเชื่อมกล้อง optical/thermal บนหอ และช่องทาง push, email, WhatsApp, SMS ([เว็บไซต์ภาษาอังกฤษ](https://www.satellitesonfire.com/en))

คู่มือในแอปอธิบายจุดสีม่วงว่าเป็น detection จาก AI ของบริษัท ขณะที่สีแดง/ส้ม/เหลืองเป็นลำดับความเป็นไปได้ที่ผู้ให้บริการกำหนด หน้ารายละเอียดจุดสามารถแสดงเวลา พิกัด ดาวเทียม และชนิดการตรวจพบได้ เหล่านี้เป็นการอธิบายผลิตภัณฑ์ ไม่ใช่หลักฐานว่า probability ผ่านการปรับเทียบทางสถิติ ([Help](https://app.satellitesonfire.com/ayuda))

Earthshot ระบุทั้งกล้องภาคพื้นและ drone feeds; เว็บไซต์หลักยืนยันกล้องอย่างชัดเจน แต่รอบนี้ไม่พบ public SDK, protocol หรือข้อกำหนดการเชื่อมโดรนที่นำมาใช้งานได้เลย จึงจัดโดรนเป็นความสามารถที่แหล่งประชาสัมพันธ์กล่าวถึง ซึ่งต้องสอบถามรายละเอียด ไม่ใช่ connector ที่ตรวจแล้วพร้อมใช้

## 2. คำกล่าวอ้างในภาพน่าเชื่อถือแค่ไหน

| ประเด็น | ตรวจพบอะไร | ใช้สรุปอะไรได้/ไม่ได้ |
|---|---|---|
| Earthshot 2026 | อยู่ในรายชื่อ **Finalist** สาขา Clean our Air จริง | ยืนยันการได้รับคัดเลือก ยังไม่ใช่ผู้ชนะหรือใบรับรอง accuracy |
| 92 ล้านเฮกตาร์ / 21 ประเทศ / 70,000 ผู้ใช้ | มีในหน้าประวัติ Earthshot | เป็นขนาดการให้บริการที่ผู้จัดเผยแพร่ ไม่ใช่พื้นที่ป่าที่พิสูจน์แล้วว่ารอดไฟทั้งหมด |
| เฉลี่ยเร็วกว่า NASA 35 นาที | Earthshot ระบุเช่นนี้ | เป็นเรื่องเวลา detection/alert ไม่ใช่ทำนายแนวไฟแม่นกว่า 35% |
| ช่วยเหตุไฟกว่า 2,000 เหตุในปี 2025 | Earthshot รายงาน | ไม่ได้บอกจำนวนไฟทั้งหมดที่พลาด จำนวน false alarms หรือการประเมินผลแบบมีกลุ่มควบคุม |
| ไฟลามด้วย AI | เว็บไซต์และ Help โฆษณาความสามารถนี้ | ไม่พบ Dice/IoU, ช่วงเวลาพยากรณ์, ชุดทดสอบไทย หรือโค้ด/น้ำหนักให้ทดสอบซ้ำ |

แหล่งข้อมูลของสี่แถวแรกคือ [Earthshot: Satellites on Fire](https://earthshotprize.org/winners-finalists/satellites-on-fire/) โดยเป็นประวัติของผู้เข้ารอบจากผู้จัดรางวัล ไม่พบรายงาน benchmark พร้อมวิธีจับคู่เวลาในหน้านี้

ตัวเลขความเร็วที่เผยแพร่ไม่เหมือนกันทั้งหมด: หน้าอังกฤษของบริษัทระบุเร็วกว่า public satellite system ได้ถึง 20 นาที ขณะที่หน้าสเปนระบุ 25 นาที; ตัวเลขกล้องมีทั้ง 3 และ 5 นาทีในหน้าเดียวกัน ส่วนกรณีศึกษา La Pampa กล่าวถึงข้อได้เปรียบราวหนึ่งชั่วโมง ([อังกฤษ](https://www.satellitesonfire.com/en), [สเปน](https://www.satellitesonfire.com/), [La Pampa](https://www.satellitesonfire.com/case-studies/la-pampa)) ความต่างอาจมาจากคนละระบบ/เหตุ/ช่วงเวลา จึงไม่ควรนำมาหาค่าเฉลี่ยเอง หรือใช้รับประกันเชียงใหม่

**รอบนี้ไม่พบ benchmark เปิดที่ระบุ sample count, ประเทศ, นิยาม NASA comparator, sensor/channel, timestamp acquisition/availability/delivery, missed fires และ false alarms ครบ** จึงยังตรวจสอบตัวเลข 35 นาทีเชิงสถิติซ้ำไม่ได้ นี่คือสถานะหลักฐานที่หาได้ ไม่ใช่ข้อสรุปว่าบริษัทไม่มีผลทดสอบภายใน

## 3. ดาวเทียมและภูมิศาสตร์: จุดที่ห้ามย้ายข้ออ้างข้ามทวีป

ไม่พบรายชื่อผลิตภัณฑ์ดาวเทียมที่ใช้ครบถ้วนจากเอกสารสาธารณะที่ตรวจ จึงไม่ระบุเองว่า SoF ใช้ GOES/VIIRS/MODIS/Himawari ใดบ้างในไทย การมีชื่อ API domain หรือแผนที่โลกไม่เพียงพอยืนยันการเปิดข้อมูลทุกพื้นที่

ตาม NOAA ระบบ GOES ปัจจุบันติดตามซีกโลกตะวันตกและแปซิฟิก จึงเอาข้ออ้างบริการทุก 10 นาทีในอเมริกามารับรองเชียงใหม่ไม่ได้ ([NOAA GOES](https://www.nesdis.noaa.gov/our-satellites/currently-flying/geostationary-satellites))

**แนวทางที่เราวิจัยต่อเองได้สำหรับเอเชียคือ Himawari** เอกสาร JMA ระบุ Full Disk รอบละ 10 นาที และย่าน 3.9/10.4 µm มีขนาดพิกเซล 2 กม. ณ จุดใต้ดาวเทียม พิกเซลจะขยายเมื่อห่างออกไป ความถี่นี้เป็นการถ่ายภาพ ไม่ใช่การรับประกันว่าทุกไฟเล็กจะถูกตรวจพบหรือข้อมูลถึงเว็บภายใน 10 นาที ([JMA AHI](https://www.data.jma.go.jp/mscweb/en/himawari89/space_segment/spsg_ahi.html))

ข้อเสนอเชิงวิศวกรรมของเรา: ใช้ geostationary เป็นหลักฐานอัปเดตสถานะ/ความรุนแรงของเหตุร่วมกับ VIIRS ที่ละเอียดกว่า ไม่แปลงพิกเซลหลายกิโลเมตรเป็นแนวไฟขนาด 20–100 เมตร และไม่ถือว่า SoF มี Himawari ให้บริการแล้วโดยไม่มีหลักฐาน

## 4. ฟรี เสียเงิน API และสิทธิใช้ข้อมูล

เงื่อนไขข้อ 3 แยกฟังก์ชันข้อมูล/แผนที่บางส่วนที่ใช้ฟรีกับบริการติดตามพื้นที่และแจ้งเตือนแบบมีค่าใช้จ่าย โดยรายละเอียดราคา พื้นที่ และระดับบริการอยู่ในข้อเสนอเฉพาะราย คู่มือแจ้งว่าราคาขึ้นกับเฮกตาร์และฟีเจอร์ ไม่พบตารางราคาเป็นตัวเลข หน้าการตั้งเตือนต้องเข้าบัญชี แม้ปุ่มระบุ Sign up free ก็ไม่ได้ยืนยันว่าทุกบริการแจ้งเตือนใช้ฟรี ([Terms](https://app.satellitesonfire.com/terms-and-conditions), [Help](https://app.satellitesonfire.com/ayuda))

| สิ่งที่จะนำมาใช้ | สถานะที่ตรวจได้ |
|---|---|
| เปิดดูแผนที่สาธารณะ | ทำได้โดยไม่สมัคร แต่ detection ไทยยังไม่เปิดแสดง |
| ตั้งพื้นที่รับเตือน | ต้องมีบัญชี; ไม่ได้สมัครหรือส่งข้อมูล |
| API | มี `api.satellitesonfire.com` ใน Terms แต่ไม่พบเอกสาร public schema/auth/quota/export ที่ยืนยันการนำมาต่อเว็บเรา |
| ดาวน์โหลดโมเดล AI / source | ไม่พบ repository/weights/open-source license ของผลิตภัณฑ์ที่ตรวจสอบได้ |
| นำข้อมูลไปแสดงเว็บเรา | ต้องตกลงสิทธิแยก ไม่ใช่ได้สิทธิเพราะเปิดดูแผนที่ได้ |

เงื่อนไขข้อ 1 และ 7 เป็นสิทธิใช้งานจำกัด และไม่ให้ถือว่ามีสิทธิแจกจ่าย/เผยแพร่ต่อหรือแก้ไขเนื้อหาของแพลตฟอร์มโดยอัตโนมัติ จึงควรใช้ public upstream ที่มีสิทธิชัดเจน หรือ API ที่บริษัทอนุญาต แทนการนำ endpoint ภายในเว็บมาทำฐานข้อมูลของเราโดยสมมติว่าเปิดเสรี

นโยบายความเป็นส่วนตัวระบุ AWS, WhatsApp, SES, Twilio และบริการเว็บอื่น มีการเก็บข้อมูลผู้รับเตือนและข้อมูลที่ผู้ใช้ส่ง รวมทั้งภาพกล้อง การเชื่อมผู้ให้บริการจึงต้องกำหนดให้ชัดว่าเก็บข้อมูลอะไร ส่งให้ใคร และใช้ฝึกโมเดลหรือไม่ก่อนให้ชุมชนใช้งาน ([Privacy](https://app.satellitesonfire.com/privacy-policy)) ไม่ได้ส่งข้อมูลชุมชนหรือภาพเข้าระบบนี้ในรอบตรวจ

## 5. สิ่งที่ควรนำมาพัฒนาระบบเราจริง

ตารางนี้เป็นข้อเสนอของการตรวจ ไม่ใช่ฟีเจอร์ที่เพิ่มแล้วหรือผล accuracy ที่พิสูจน์แล้ว

| ลำดับ | งานที่นำมาปรับใช้ | ฐานใน repo ที่ตรวจพบ | วัดผลอย่างไร |
|---|---|---|---|
| 1 | แยกเวลา sensor ตรวจพบ → provider เผยแพร่ → เว็บรับ → ส่งเตือน → ผู้ใช้เห็น | `backend/app/models.py` มี provenance/freshness และ `backend/app/community_field.py` มีสถิติเวลาบางช่วง | median/P90 นาทีทุกช่วง แยกต้นทางและข้อมูลขาด |
| 2 | รวมจุดหลายแหล่งให้เป็นเหตุเดียว พร้อมเหตุผล/หลักฐาน | `backend/app/providers/hotspot_provider.py` และ `Hotspot.source_observations` | เหตุซ้ำต่อวัน, false merge, ข้อมูลจริงต่อเหตุ |
| 3 | เตือนตามขอบเขตป่าชุมชนและผู้รับผิดชอบ ดูไฟข้างเคียงด้วย | ข้อมูลขอบเขต 677 ป่า, `community_mail.py` มี opt-in/outbox/callback | เหตุที่เกี่ยวข้องและได้รับการเห็น, จำนวนการเตือนเกินต่อป่า/วัน |
| 4 | หน้าตรวจสอบเหตุที่สั้นและใช้งานได้บนมือถือ | มี community incident/field/evidence API | เวลากดเปิดจนยืนยันสถานะ, การเปิดสำเร็จบนเครือข่ายช้า |
| 5 | แสดงภาพกล้อง/รายงานคนร่วมกับ hotspot โดยบอกตำแหน่ง มุมมอง และอายุภาพ | `public_cameras.py` แยกภาพสด ภาพเก่า และ source-only | จำนวนหลักฐานที่ช่วยยืนยัน/หักล้างจริง; ไม่ถือกล้องแม่น้ำเป็นกล้องตรวจไฟป่าโดยอัตโนมัติ |
| 6 | ทดลอง Himawari ร่วมกับ VIIRS แบบออฟไลน์ | ยังไม่พบ Himawari ingestion ใน `backend/app` จากการค้นรอบนี้ | detection lead time, precision/recall รายเหตุ, misses ของไฟเล็ก |
| 7 | อัปเดตจุดเริ่มแบบจำลองตามข้อมูลใหม่และเก็บทุก forecast version | `forecast_archive.py`, `environment_archive.py` มีพื้นฐานคลังเวลา | Dice/IoU ของ **การลามใหม่** ที่ 1/3/6/12 ชม. เทียบการไม่อัปเดตและฐานง่าย บนเหตุที่กันออกจากการปรับค่า |

ข้อ 1–5 ช่วยทำ Dashboard ให้มีประโยชน์โดยไม่ต้องรอให้แบบจำลองแนวไฟสมบูรณ์ ส่วนข้อ 6–7 มีโอกาสช่วยความแม่นของสถานะ/พยากรณ์ แต่ต้องทดสอบก่อนอ้างผล ปุ่ม/โครงสร้าง backend ที่มีใน source ไม่ได้หมายความว่า deployment เปิดทุกบริการแล้ว เช่น `community_email_enabled` ยังมีค่าเริ่มต้น false; รอบนี้ไม่ตรวจ credentials หรือสถานะส่งข้อความ production

**สำหรับ PM2.5:** การตรวจพบไฟเร็วและรู้กำลังไฟตามเวลาช่วยให้ออกแบบ emission input ได้ดีขึ้น แต่ไม่ได้เท่ากับพยากรณ์ความเข้มข้น PM2.5 ที่พื้นได้แล้ว ยังต้องลมหลายระดับ ความสูงชั้นผสม การเคลื่อนที่/ตกสะสมและเทียบสถานีจริง ไม่พบหลักฐานว่า SoF เปิดโมเดล PM2.5 สำหรับไทยให้ใช้

## 6. ถ้าจะเปรียบเทียบกับผู้ให้บริการโดยตรง

ต้องได้ export สำหรับเหตุเชียงใหม่ที่มีเวลาออกผลจริง ไม่ใช่แผนที่ที่ดึงย้อนหลังหลังรู้ผลแล้ว: event id, sensor/product, observation/processing/available/alert timestamps, confidence definition, geometry, prediction issue/valid times, cloud/coverage mask และสิทธิประเมิน/เผยแพร่ผล จากนั้นกันชุดเหตุออกล่วงหน้าและเปรียบเทียบกับ pipeline เดิมบนช่วงเวลาเดียวกัน

งานตรวจพบให้ใช้ precision/recall และเวลาพบครั้งแรกหลังเริ่มเหตุที่มีหลักฐาน ไม่เทียบกับเฉพาะเหตุที่ vendor ตรวจพบสำเร็จ งานแนวไฟให้ใช้พื้นที่ลามเพิ่ม/IoU/Dice, พื้นที่ทำนายเกิน, พื้นที่พลาด และ boundary distance โดยตรึงเวลาทำนาย แยกไฟใหม่ออกจากการลามของไฟเดิม งานชุมชนให้ใช้จำนวนการเตือนและเวลารับทราบต่อขอบเขตป่าพร้อมผลตรวจภายหลัง ทั้งสามงานนี้ไม่มี “accuracy เดียว” ทดแทนกัน

## สถานะการตรวจรอบนี้

ตรวจเอกสารสาธารณะและเว็บแอปจริงแล้ว; หน้า Help และ Terms อ่านจาก UI เพราะ web text parser อ่านบางหน้าไม่ได้ ไม่ได้สมัครบัญชี ขอ trial ติดต่อบริษัท ส่งรายงานไฟ จ่ายเงิน ต่อ API ลับ เปลี่ยนเว็บเรา หรือ deploy ผลที่ส่งมอบคือการประเมินต้นทางและรายการงานที่มีเหตุผลรองรับ ไม่ใช่ผลรันโมเดล SoF บนเชียงใหม่
