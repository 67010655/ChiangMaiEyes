# แผนชุดถัดไป: พื้นที่ป่าชุมชนและการประสานเหตุ

วันที่วางแผน: 9 ตุลาคม 2026

สถานะการทำงาน: [ผลปล่อยและตรวจชุด 2](./2026-10-09-community-release.md) — ขึ้น production สำหรับทดลองแล้ว; การส่งอีเมลทั่วไปและ pilot กับตัวแทนจริงยังรอตรวจรับตามข้อจำกัดในบันทึก

## เป้าหมาย

ตัวแทนที่ได้รับการยืนยันเข้าเว็บแล้วเห็นป่าของตนเอง รู้ว่ามีข้อมูลใดควรตรวจสอบ บันทึกเหตุได้สั้น ๆ เห็นผู้รับประสานและชุมชนที่ร่วมช่วย และรับอีเมลที่มีที่มาและเวลา ระบบเก็บประวัติต่อเนื่องหลังเหตุจบ

แผนนี้อิงโค้ดใน repo และบันทึกการปล่อยชุดแรก ไม่ได้ยืนยันว่า Supabase production ใช้ schema/policy ตรงกับ migration ที่อยู่ใน repo

## ข้อค้นพบที่กำหนดลำดับงาน

- Production ใช้ `frontend/index.html` และส่งข้อมูลเข้า `manual_hotspot_reports`; React scaffold ใช้ `field_reports`; backend provider มี `field_activity_reports` ต้องตรวจตารางที่มีจริงและกำหนดความสัมพันธ์ก่อนเพิ่ม incident workflow
- Migration `supabase/migrations/20260621065819_auth_user_reports.sql` ให้ authenticated insert profiles ได้ทั้งแถว และ INSERT policy ตรวจเฉพาะ id จึงยังไม่กันการส่ง role ที่มีสิทธิ์สูงตอนสร้างแถว ส่วน community_id แก้โดยเจ้าของแถวได้ ไม่ควรใช้เป็นหลักฐานสมาชิกที่ยืนยันแล้ว
- Migration ดังกล่าวให้ insert field_reports ได้ทั้งแถว และตรวจเฉพาะ user_id ต้องป้องกันการกำหนด verification_status/verified_by/verified_at โดยผู้ส่งเองด้วย
- การเก็บรายงานเดิมที่ไม่แสดงบนแผนที่หลัง 3 วัน ไม่ใช่ incident register ที่มีการรับเรื่องและประวัติการเปลี่ยนสถานะ
- ยังไม่มี Resend/outbox ในโค้ดที่ตรวจรอบนี้; ต้องตรวจบัญชี โดเมน และ deployment configuration ที่มีจริง

## ลำดับงานและผลตรวจรับ

| ช่วง | งาน | เกณฑ์ตรวจรับ |
|---|---|---|
| 2A ฐานข้อมูลและสิทธิ์ | ตรวจ deployed schema/grants/RLS, สำรองข้อมูลก่อน migration, แก้การตั้ง role/สถานะยืนยันเอง, เพิ่มสมาชิกป่าที่ต้องอนุมัติ, ตรวจ dependency audit และ export PDF ค้าง | ผู้ใช้ตั้งตนเองเป็น admin หรือสมาชิกป่าอื่นไม่ได้; ผู้ส่งยืนยันรายงานตนเองไม่ได้; ข้อมูลเดิมคงอยู่; migrations มีแผนย้อนกลับ |
| 2B ป่าของฉัน | ตัวแทนยืนยันแล้วเห็นข้อมูลเฉพาะ polygon ของป่าตน, แผนที่, งานรอตรวจสอบ, ช่องทางประสาน และประวัติ; ผู้ดูแลมีคิวอนุมัติ | ล็อกอินแล้วไปพื้นที่ที่อนุมัติจริง; สลับป่าได้เฉพาะสมาชิกที่มีสิทธิ์; ทดสอบป่าคนละแห่งแล้วเข้าถึงข้อมูลส่วนตัวข้ามกันไม่ได้ |
| 2C บันทึกและประสานเหตุ | แบบแจ้งสั้น, ร่างและ retry, incident timeline, รวมรายงานที่เป็นเหตุเดียวกัน, ระบุผู้รับประสานและชุมชนสนับสนุน, เปลี่ยนหน้าเฟสไฟเป็นติดตามเหตุ | refresh แล้วยังมีเหตุ; สองชุมชนร่วมเหตุเดียวกันได้; สถานะ/ผู้เปลี่ยน/เวลาอยู่ครบ; รายงานซ้ำไม่เพิ่มจำนวนเหตุโดยอัตโนมัติ |
| 2D อีเมล Resend | ยินยอมรับอีเมล, แยกเหตุใหม่กับสรุปรายวัน, server-side matching, outbox, dedup, retry, delivery/bounce handling | ส่งถูกผู้รับและพื้นที่; retry ไม่ส่งข้อความเดิมซ้ำ; ยกเลิกรับได้; ข้อมูลเก่า/ขาดหายไม่ถูกแปลงเป็นเหตุเตือนใหม่; ตรวจอีเมลที่ได้รับจริง |
| 2E ทดลองและปล่อย | desktop/mobile, dark/light, reduced motion, keyboard, สัญญาณช้า/หลุด, ทดสอบหลายผู้ใช้, pilot และ production smoke test | วัดเวลาแจ้งเหตุ/หาเจ้าของเรื่อง, API latency/error/DB load; ใช้ผู้ทดลองที่ยืนยันจริง; ดูผล preview ก่อน promote |

2A และ 2B ต้องเสร็จก่อนเปิดใช้บัญชีตัวแทนจริง; 2C ต้องมีสถานะและข้อมูลเหตุที่ชัดเจนก่อนเปิดอีเมลเหตุอัตโนมัติ

## UX ที่จะเพิ่ม

- เมนู “ป่าของฉัน” สำหรับตัวแทนที่ได้รับอนุมัติ
- ส่วนบนสั้น: จุดที่ควรตรวจสอบ / ฝุ่น / ลม พร้อมเวลาและขอบเขตการวัด
- รายการ “งานที่ต้องดู” เรียงเหตุใหม่และเหตุที่รอรับประสาน ไม่ขึ้นกราฟทั้งหมดตั้งแต่เปิด
- แบบแจ้งเริ่มจากตำแหน่ง เวลา และสิ่งที่พบ; รูปและรายละเอียดเติมภายหลังได้ เก็บเวลารับรายงานแยกจากเวลาที่เห็นเหตุ
- แสดงเวลาบันทึกร่างล่าสุดและสถานะส่ง ไม่ทำให้ผู้ใช้คิดว่าส่งแล้วเมื่อยังไม่มี network acknowledgement
- สถานะหลัก: รอตรวจสอบ → ยืนยันเหตุ → กำลังประสาน → ควบคุมได้ → ปิดเหตุ; มีเหตุยกเลิก/ไม่พบไฟพร้อมเหตุผล และเหตุเปิดใหม่เมื่อมีหลักฐานเพิ่ม
- การรับเรื่องและรายชื่อผู้ร่วมช่วยเป็นการยืนยันจากคนที่มีสิทธิ์ ไม่ตีความผู้สั่งการจากอำเภอหรือ polygon อัตโนมัติ
- ข้อมูลผู้แจ้ง/พิกัดละเอียด/หลักฐานมีขอบเขตสิทธิ์; public view แสดงเฉพาะส่วนที่อนุมัติให้เผยแพร่
- ใช้สีและ animation เดิมเพื่อบอกการกด การเปลี่ยนสถานะ และผลการบันทึก พร้อมรองรับ reduced motion

## กติกาอีเมล

- ผู้รับต้องเป็นสมาชิกที่อนุมัติแล้ว มีอีเมลยืนยันและเลือกเปิดรับ
- เมื่อข้อมูลดาวเทียมใหม่เข้า polygon ที่ติดตาม ให้ข้อความว่า “พบจุดความร้อนจากดาวเทียม รอการตรวจสอบ” ไม่เรียกเป็นไฟที่ยืนยันแล้ว
- การยืนยันเหตุและคำขอประสานส่งตามขอบเขตผู้รับที่กำหนด ไม่เผยข้อมูลส่วนตัวให้ทั้งจังหวัด
- สรุปรายวันรวมสถานการณ์ เวลา แหล่งข้อมูล ข้อมูลที่ยังไม่ครบ และลิงก์เข้าป่าของตน
- ตั้งกติกาเงียบ/รวมข้อความและ threshold โดยทดสอบกับข้อมูลย้อนหลังและผู้ทดลอง ไม่เลือกตัวเลขความเสี่ยงโดยเดา
- เก็บ unique event/recipient/message key ในฐานข้อมูล และใช้ Resend idempotency key เพิ่มเติม; provider เก็บ key 24 ชั่วโมง จึงไม่ใช้เป็นประวัติ dedup ระยะยาวเพียงอย่างเดียว
- เก็บ API key ฝั่ง server; ตรวจโดเมนผู้ส่งที่เจ้าของควบคุมและยืนยันแล้วก่อนส่งจริง

อ้างอิง: [Resend domains](https://resend.com/docs/dashboard/domains/introduction), [Resend idempotency](https://resend.com/docs/dashboard/emails/idempotency-keys), [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security)

## ข้อมูลและการตัดสินใจที่ต้องยืนยัน

- Supabase project/schema/policies ปัจจุบันและตาราง manual_hotspot_reports ที่ frontend ใช้
- ใครมีอำนาจอนุมัติตัวแทนและผู้ประสานในระบบ; รายชื่อจากเว็บไซต์สาธารณะใช้เป็นช่องทางติดต่อ ไม่ใช้รับรองตัวตนหรืออำนาจสั่งการโดยอัตโนมัติ
- บัญชี Resend, โดเมนผู้ส่ง, สิทธิ์ DNS และงบ/โควตาที่มีจริง
- ชุมชนทดลอง: ใช้ดอยปุยเป็นผู้สมัครที่เป็นไปได้จาก feedback ที่ผู้ใช้ให้ แต่ยังไม่ถือว่าได้รับความร่วมมือหรือมีตัวแทนยืนยัน; เลือกอีกพื้นที่เมื่อมีผู้ร่วมทดลองจริงเพื่อทดสอบข้ามชุมชน

## งานชุดหลังจากนี้

### ชุด 3: ข้อมูลและแบบจำลอง

- เก็บ hotspot/weather/incident ย้อนหลังต่อเนื่องพร้อม provenance และตรวจความครบของ 30 วัน
- ต่อ GFS/PBL/ventilation หลังตรวจความละเอียด เวลา รอบอัปเดต และหน่วยของ product
- ทำ baseline การลามที่อ่าน DEM/slope และข้อมูลเชื้อเพลิงจริง ใช้ระดับเชื้อเพลิงเมื่อมีวิธีแปลงและสอบเทียบที่อ้างอิงได้
- สร้างภาคสนาม dataset: เวลา/ขอบเขตไฟ/เชื้อเพลิง/อากาศ/ผลการตรวจสอบ; วัด false alarms, missed events และความคลาดเคลื่อนเชิงพื้นที่/เวลา
- พิจารณา ML หลังมี baseline และ ground truth; แยกพื้นที่/เวลาทดสอบเพื่อไม่ให้ข้อมูลอนาคตหรือเหตุเดียวกันรั่วไป training
- แสดง forecast เท่าที่ provider/model รองรับจริง; ความต้องการหน้า 30 วันไม่ใช่เหตุให้สร้างคำทำนายไฟรายจุด 30 วันขึ้นเอง

### ชุด 4: กล้องและข้อมูลประกอบ

- ตรวจ feed, พิกัด, เวลาไฟล์ และสิทธิ์ reuse ของกล้องสาธารณะที่พบ
- ฝังเฉพาะแหล่งที่อนุญาต; หากยังไม่อนุญาตให้เป็นลิงก์ต้นทางพร้อมสถานะ ไม่เรียกภาพย้อนหลังว่าสด
- เพิ่มโลโก้จาก assets ทางการที่ตรวจสิทธิ์แล้ว และช่องทางติดต่อแต่ละป่าจากแหล่งเผยแพร่ที่ยืนยัน
- พื้นที่เผาไหม้ต้องมี polygon จาก product ที่ระบุได้ พร้อมสถานะยังไม่ยืนยัน/ยืนยันและช่องทางแก้ไขข้อมูล

### ชุด 5: แรงจูงใจ

- ให้คะแนนความพร้อม เช่น ตรวจแหล่งน้ำ ทำแนวกันไฟ อัปเดตผู้ประสาน และบันทึกข้อมูลที่ผ่านตรวจ
- ออกแบบเกณฑ์ให้เทียบกับทรัพยากร/ขนาดพื้นที่อย่างเหมาะสมก่อน ranking
- ทดสอบว่าคะแนนไม่สร้างแรงจูงใจให้เข้าพื้นที่อันตรายหรือรายงานเกินจริง; ไม่นำจำนวนครั้งที่เข้าดับไฟเสี่ยงเป็นเกณฑ์รางวัล

## การแบ่ง deploy

ปล่อยเมื่อแต่ละช่วงมีผลที่ใช้งานได้ครบและผ่านเกณฑ์ของช่วงนั้น: ฐานสิทธิ์ → ป่าของฉัน → ติดตามเหตุ → อีเมล เริ่มด้วย preview และผู้ทดสอบที่ยืนยันก่อนเปิดวงกว้าง เก็บ migration/deployment revision และตรวจหน้าเว็บ/API/ข้อมูลหลัง promote ทุกครั้ง
