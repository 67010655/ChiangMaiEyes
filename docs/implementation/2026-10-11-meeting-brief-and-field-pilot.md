# ChiangMaiEyes: สรุปประชุมและแผนทดลองภาคสนาม

สำหรับประชุม 11 ตุลาคม 2026 · จัดทำ 10 ตุลาคม 2026

อิงโค้ดปัจจุบัน บันทึกปล่อยและผลตรวจ 9 ตุลาคม รวมถึง feedback จากหน่วยงานและชุมชนที่ผู้ใช้ให้ ไม่ถือผลทดสอบซอฟต์แวร์เป็นผลทดสอบการใช้งานภาคสนาม

## 1. ประโยคเปิดประชุม

> ตอนนี้ ChiangMaiEyes ปรับทั้งการอ่านข้อมูลและการประสานเหตุแล้วครับ เราลดข้อมูลที่ซ้ำ แยกข้อมูลดาวเทียมออกจากเหตุที่คนยืนยัน และทำพื้นที่ป่าชุมชนให้ผู้รับผิดชอบบันทึกและติดตามเหตุร่วมกันได้ ขอบเขตยังยึดข้อมูลจริง 677 ระเบียนที่ได้รับผ่าน RECOFTC ส่วนอีเมลส่งทดสอบได้แล้ว แต่ยังไม่เปิดให้ผู้รับทั่วไป และแบบจำลองการลามยังต้องเก็บข้อมูลกับทดสอบภาคสนามก่อน สิ่งที่อยากขอจากการประชุมครั้งนี้คือชุมชนทดลอง ผู้ประสานที่ตรวจสอบได้ และตกลงร่วมกันว่าเว็บต้องช่วยให้งานขั้นตอนไหนดีขึ้นครับ

## 2. อัปเดตงานที่ทำแล้ว

| เรื่อง | ปรับอะไรไปแล้ว | ประโยชน์ต่อคนใช้ / ขอบเขตผล |
|---|---|---|
| UX/UI | ลดข้อมูลซ้ำ เช่น ทิศทางลม แยกสรุปสั้นกับข้อมูลละเอียด แก้เมนูและหน้าซ้อน อ่าน dark/light ได้ชัดขึ้น มี hover/กด/เปลี่ยนสถานะและ reduced motion | เข้าเว็บแล้วเห็นสถานการณ์สำคัญก่อน รายละเอียดค่อยเปิดตามงาน |
| ความหมายของข้อมูล | แสดงแหล่งข้อมูลและเวลา แยกเวลา satellite ตรวจพบกับเวลาเว็บรับข้อมูล ไม่ใส่กราฟตัวอย่างหรือสร้างค่าศูนย์เมื่อข้อมูลขาด | ไม่ทำให้ “ไม่มีข้อมูล” กลายเป็น “ไม่มีไฟ” |
| ลม | ลมเคลื่อนไหวกับลูกศรแบบจำลองใช้ข้อมูลชุดเดียวกัน เปิดสลับกัน แยกลมสถานีจากแบบจำลองและระบุระดับเมื่อแหล่งข้อมูลมี | ลดปัญหาลูกศรขัดกัน ยังไม่ถือว่าลมอ้างอิงจังหวัดเป็นลมในป่าทุกแห่ง |
| แผนที่และ 3D | ใช้ polygon จริง 677 ระเบียน เปิด terrain ต่อเนื่อง เพิ่มปุ่มดูภูเขา โหลดส่วนหนักเมื่อจำเป็น | ใช้สำรวจภูมิประเทศได้ การแสดง DEM ใน 3D ยังไม่แปลว่าแบบจำลองลามอ่าน DEM แล้ว |
| ป่าของฉัน | บัญชีตัวแทนต้องได้รับอนุมัติพื้นที่ก่อน เห็นข้อมูลในขอบเขตป่าและงานที่เกี่ยวข้อง ผู้ดูแลมีคิวคำขอ | การสมัครหรือเลือกชื่อป่าไม่เท่ากับได้รับสิทธิ์ |
| บันทึกเหตุ | แจ้งควัน/เปลวไฟ ตำแหน่ง เวลา รายละเอียด เก็บร่างแยกบัญชี ส่งซ้ำใช้รหัสเดิม มีประวัติผู้เปลี่ยนและเหตุผล | ส่งง่ายขึ้นและมีประวัติต่อเนื่อง ไม่ใช่หมุดที่หายแล้วไม่มีทะเบียนเหตุ |
| ประสานงาน | รับเป็นผู้ประสาน เชิญชุมชนอื่น รับ/ไม่รับคำขอ เปลี่ยนสถานะ และเชื่อมรายงานซ้ำกับเหตุหลัก | ต้องมีคนที่มีสิทธิ์ยืนยัน ไม่แต่งตั้งผู้สั่งการจากเส้นขอบเขตอัตโนมัติ |
| รูปและความเป็นส่วนตัว | รูปอยู่ในพื้นที่ส่วนตัว ตรวจชนิด/ขนาดไฟล์และลบ EXIF สรุปสาธารณะแสดงเฉพาะส่วนที่เลือกเผยแพร่ | การเชิญชุมชนอื่นทำให้ตัวแทนที่ได้รับสิทธิ์ดูรายละเอียดเหตุได้ ต้องเข้าใจการแบ่งปันนี้ |
| อีเมล | Resend, การยินยอมรับ/หยุดรับ เวลาพัก คิวส่ง ป้องกันซ้ำ retry และผลนำส่ง ส่งทดสอบจริงและ callback ยืนยันแล้ว | ตรวจ API วันนี้ได้ `email_mode=test` ยังไม่เปิดส่งถึงสมาชิกทั่วไป |
| รายงานส่งออก | เลือกพื้นที่และ 24/72 ชั่วโมง เลือกองค์ประกอบ PNG เปิดตรวจแล้ว PDF print rendering เปิดอ่านและดูทั้งสองหน้าแล้ว แก้ไม่ให้หน้าส่วนตัวติดไป | รายงานตรงกับพื้นที่และเวลาที่เลือก มีแหล่งข้อมูลและข้อจำกัด |

**หลักฐานตรวจ 9 ตุลาคม:** API tests 113 ผ่าน; frontend/SQL tests 67 ผ่าน; desktop/mobile และ dark/light ตรวจแล้ว; read test 12 requests พร้อมกันสูงสุด 4 คำขอได้ HTTP 200 ทั้งหมด median 1.79 วินาที และ p95 5.42 วินาที ตัวอย่างนี้ยังไม่ใช่หลักฐานรองรับการใช้พร้อมกันทั้งจังหวัด

**ตรวจเพิ่ม 10 ตุลาคม:** `/api/community/status` ตอบ HTTP 200, `ready=true`, `email_mode=test`, `private_records=true` เป็นการตรวจสถานะ API ไม่ใช่การตรวจทุกหน้าหรือทุกบัญชีซ้ำในวันนี้

## 3. สิ่งที่ยังไม่ควรนำเสนอว่าเสร็จแล้ว

- ยังไม่มี pilot กับตัวแทนชุมชนจริง จึงยังไม่มีผลว่าเว็บทำให้แจ้งเหตุหรือประสานงานเร็วขึ้นเท่าไร
- ต้องยืนยันโดเมนผู้ส่ง ตรวจ Auth SMTP/redirect และทดสอบการสมัครกับอีเมลตัวแทนทั่วไปก่อนเปิดวงกว้าง
- ต้องกำหนดรอบตรวจข้อมูล/ส่งอีเมลที่แน่นอน การมี worker ไม่ใช่การรับรองว่าจะเตือนทุก 5 นาทีเมื่อไม่มี traffic
- ยังไม่มีหัวหน้าป่าหรือผู้รับผิดชอบรายแห่งที่ตรวจสอบครบ ข้อมูล RECOFTC ที่ได้รับเป็นขอบเขต ไม่ใช่ทะเบียนบุคลากรหรือผู้สั่งการ
- กล้อง CCDC พบตัวเลือกภาพ snapshot แต่ยังไม่เชื่อมกล้องสดเข้า production ต้องตรวจเวลาไฟล์ พิกัด และสิทธิ์ reuse
- กรวยปลายลมเป็นภาพประกอบ ไม่ใช่ผลพยากรณ์การลามที่ผ่าน validation
- การเปิด terrain ใน 3D ยังไม่ได้แก้แบบจำลองให้ใช้ DEM/slope/fuel จริงครบ และยังไม่ได้สอบเทียบภาคสนาม
- EVI แสดงความเขียวของพืชพรรณ ยังไม่ได้แปลงเป็นปริมาณเชื้อเพลิงแห้งที่ผ่านการสอบเทียบ
- สีคะแนนเฝ้าระวังรายอำเภอไม่ใช่พื้นที่เผาไหม้จริง ยังไม่มี burned-area polygons ที่ผ่านยืนยัน
- ยังไม่ได้เชื่อม GFS/PBL/ventilation และยังไม่ได้ train/รับรอง ML ไม่เสนอพยากรณ์ไฟรายจุด 30 วัน

## 4. แผนต่อไปที่เสนอในที่ประชุม

| ลำดับ | งาน | สิ่งที่ต้องได้ก่อนขยับต่อ |
|---|---|---|
| 1. เตรียม pilot | เลือกชุมชนและตัวแทน ตรวจสิทธิ์/ขั้นตอนรับเรื่อง เตรียมระบบซ้อมแยกจากเหตุจริง แก้อีเมลทั่วไปและรอบงาน | ผู้ประสานยืนยันได้ บัญชีใช้งานได้จริง และไม่มีการส่งเหตุซ้อมไปเป็นการเตือนจริง |
| 2. ทดลองงานจริงของคน | ทดลองอ่านข้อมูล แจ้งเหตุ ประสานสองชุมชน ส่งออก และกรณีเน็ตหลุด เก็บ feedback และเวลา | มีผลวัดและรายการแก้ UX จากผู้ใช้จริง |
| 3. สร้างข้อมูลอ้างอิงภาคสนาม | จับคู่ hotspot กับรายงานคน เก็บเวลา ตำแหน่ง ขอบเขต หลักฐาน อากาศ/เชื้อเพลิงที่มีวิธีวัด | ข้อมูลมี provenance, ขอบเขตความคลาดเคลื่อน และแยก “ยังไม่ตรวจ” จาก “ตรวจแล้วไม่พบ” |
| 4. ทำ baseline แบบจำลอง | ใช้ DEM/slope และเชื้อเพลิงที่อ้างอิงได้ ตรวจ GFS/PBL/ventilation และเปรียบกับ baseline ง่าย ๆ | รายงาน false alarms, missed events และความคลาดเคลื่อนพื้นที่/เวลา จากชุดทดสอบอิสระ |
| 5. กล้องและข้อมูลเสริม | ต่อแหล่งที่ตรวจสิทธิ์และเวลาแล้ว เพิ่มช่องทางผู้ประสานและ correction workflow | แยกภาพสด/ภาพย้อนหลังได้ และเจ้าของข้อมูลยินยอมตามขอบเขตใช้งาน |
| 6. ML/คะแนนความพร้อม | ทำเมื่อมีข้อมูลและ baseline; คะแนนเน้นความพร้อมและคุณภาพข้อมูล | ไม่ใช้เหตุเดียวกันหรือข้อมูลอนาคตปนชุดฝึก/ทดสอบ และไม่ให้รางวัลจากการเข้าดับไฟที่เสี่ยง |

แนะนำ deploy เป็นชุดที่ใช้งานได้ครบและตรวจรับแล้ว เก็บ revision/หลักฐาน ไม่รอรวมทุกเรื่องจนปล่อยครั้งเดียว

## 5. ถ้าไปเชียงใหม่ ต้องทดลองอะไรบ้าง

### เป้าหมายของการลงพื้นที่ครั้งแรก

ตอบให้ได้ว่า **คนเข้าใจข้อมูลไหม แจ้งและส่งต่อเรื่องได้ไหม และข้อมูลไหนตรงหรือไม่ตรงกับพื้นที่จริง** การไปครั้งแรกยังไม่ใช่การรับรอง accuracy ของการพยากรณ์ไฟทั้งจังหวัด

**ข้อเสนอสำหรับหารือ:** 2 ชุมชน ผู้ทดลองรวมประมาณ 8–12 คน และหน่วยงานที่เกี่ยวข้อง เริ่มทดสอบแบบมีผู้สังเกต 2 วันถ้าการเดินทางเอื้อ แล้วติดตามการใช้ 7–14 วัน ตัวเลขนี้เป็นแผนเบื้องต้น ไม่ใช่รายชื่อหรือกำหนดการที่ยืนยัน และช่วงติดตามนี้ไม่ใช่ระยะสอบเทียบเซนเซอร์ตามมาตรฐาน

เลือกชุมชนที่ยินดีร่วมและมีผู้ประสานยืนยันได้ พิจารณาให้มีความต่างด้านสัญญาณมือถือหรือภูมิประเทศ ดอยปุยเป็นเพียงตัวเลือกจาก feedback เดิม ยังไม่ถือว่าตกลงร่วมทดลองแล้ว

| การทดลอง | วิธีทำ | สิ่งที่วัด/บันทึก |
|---|---|---|
| A. อ่านหน้าเว็บ | ให้ดูหน้าแรกและป่าของตนโดยยังไม่สอน ถามว่าข้อมูลบอกอะไร เวลาไหน และควรทำอะไรต่อ | เวลาที่อธิบายถูก จำนวนคนที่สับสนว่าหมุดคือไฟที่ยืนยันแล้ว ลมพัดมาหรือพัดไป และข้อมูลจังหวัดกับข้อมูลในป่า |
| B. แจ้งเหตุบนมือถือ | ใช้สถานการณ์ซ้อมที่ระบุชัดในระบบแยก ให้เลือกตำแหน่ง กรอกเวลา ส่ง แล้วเติมรูป/รายละเอียด ลองจุดสาธารณะบนแผนที่ที่ตกลงไว้ | ทำสำเร็จเองหรือได้รับความช่วยเหลือ เวลาต่อขั้นตอน จุดกดผิด ความคลาดเคลื่อนตำแหน่ง ความเข้าใจ “ร่าง” กับ “ส่งแล้ว” |
| C. เน็ตช้า/หลุด | เปิดเว็บขณะมีเน็ตก่อน แล้วจำลองหลุดระหว่างกรอกหรือส่ง ต่อเน็ตและ retry; ทดลองรีเฟรชหลังบันทึกสำเร็จ | ร่างหายหรือไม่ มีเหตุซ้ำหรือไม่ รูปสำเร็จจริงหรือไม่ ผู้ใช้เข้าใจสถานะส่งไหม อย่าอ้างว่าร่างในเครื่องทำให้เว็บเป็นระบบ offline เต็มรูปแบบ |
| D. ประสานสองชุมชน | คน A รับประสาน เชิญ B ให้ B รับ/ไม่รับ เปลี่ยนสถานะพร้อมเหตุผล เชื่อมรายงานซ้ำและย้อนดูประวัติ | ใช้เวลาหาผู้รับเรื่องเท่าไร งานค้างที่ขั้นไหน สถานะเข้าใจตรงกันไหม คนที่ไม่มีสิทธิ์เห็น/แก้ข้อมูลได้หรือไม่ |
| E. อีเมล | เมื่อโดเมน/บัญชีพร้อม ให้ผู้ทดลอง opt-in ทดลองเหตุและสรุป เวลาพัก หยุดรับ และส่งซ้ำ | เวลาเข้าคิว → provider รับ → นำส่ง → ผู้ใช้เห็นจริง ตรวจ Spam และการเปิดใช้ อีเมลมาช้าอาจอยู่คนละขั้นกับข้อมูลดาวเทียม |
| F. ขอบเขตป่า/ตำแหน่ง | ให้เจ้าของพื้นที่ชี้ป่าของตนและจุดเข้าถึง สุ่มจุดทางเข้า/จุดอ้างอิงที่ปลอดภัย เปรียบ GIS กับ GPS และข้อมูลหน่วยงาน | ชื่อ/รหัส/แปลงถูกไหม ตำแหน่งคลาดเท่าไร GPS accuracy เท่าไร เส้นทางใช้ได้จริงไหม ไม่แก้ขอบเขตทางการจาก GPS โทรศัพท์ไม่กี่จุด |
| G. Hotspot กับหลักฐานคน | ใช้รายงานย้อนหลังที่มีเวลา/พิกัดและเหตุที่ทีมมีอำนาจตรวจ บันทึกพบไฟ/ไม่พบ/ยังตรวจไม่ได้ และเชื่อม satellite pass/product | เวลาเห็นเหตุ/ดาวเทียมตรวจพบ/เว็บรับ/แจ้งเตือน ระยะหรือ pixel footprint ความมั่นใจ และเหตุที่ดาวเทียมไม่พบ เก็บทั้งกรณีตรวจพบและกรณีไฟที่ทราบแต่ไม่มี hotspot |
| H. ลม ฝุ่น และเชื้อเพลิง | ถ้ามีเครื่องมือและวิธีวัดที่ตกลงกับผู้เชี่ยวชาญ เก็บลม/อุณหภูมิ/RH พร้อมที่ตั้งและความสูง; PM เทียบเครื่องอ้างอิงที่เวลาและจุดเดียวกัน; ถ่ายภาพ/บันทึกเชื้อเพลิงตามแบบฟอร์มเดียวกัน | ลม m/s หรือ km/h และทิศแบบเดียวกัน, PM2.5 µg/m³, RH %, เวลา/ความสูง/รุ่นเครื่อง/การสอบเทียบ เชื้อเพลิงยังไม่ใช้ EVI เป็นค่าจริงแทนการวัด |

### ข้อควรระวังในการตีความผล

- NASA อธิบายว่า hotspot ของ MODIS เป็นจุดกึ่งกลาง pixel ที่ตรวจพบความร้อน ไม่จำเป็นต้องเป็นพิกัดจุดไฟจริง จึงต้องจับคู่ตามเวลาและ footprint ไม่สรุปว่า GPS คลาดกับหมุดเท่ากับ satellite ผิดทั้งหมด [NASA FIRMS FAQ](https://forum.earthdata.nasa.gov/viewtopic.php?t=5191)
- การตรวจจุด hotspot อย่างเดียววัดได้แค่ความถูกต้องของรายการที่ตรวจ ไม่รู้ missed events ต้องมีรายงานเหตุที่ยืนยันจากคนอีกชุด รวมถึงเหตุที่ไม่มี hotspot และแยกยังตรวจไม่ได้ออกจากผลลบ
- PM sensor ราคาต่ำควรทดสอบวางใกล้เครื่องอ้างอิง ณ เวลาเดียวกัน และเก็บอุณหภูมิ/RH ประกอบ EPA ระบุว่าความชื้นและอุณหภูมิอาจกระทบค่า การเทียบกับสถานีคนละจุดไม่ใช่การสอบเทียบเครื่องโดยตรง [EPA Collocation Guide](https://www.epa.gov/air-sensor-toolbox/air-sensor-collocation-instruction-guide), [EPA FAQ](https://www.epa.gov/air-sensor-toolbox/frequent-questions-about-air-sensors)
- การสำรวจลมด้วยเครื่องถือใกล้พื้นไม่ใช่ reference ที่ระดับ 10 เมตรโดยอัตโนมัติ ต้องบันทึกบริบทการวัดและไม่สรุป model accuracy จากข้อมูลต่างระดับ/ต่างตำแหน่ง
- ไม่จุดไฟเพื่อสร้างเหตุทดสอบ ไม่ให้ทีมเว็บหรือชาวบ้านที่ไม่ได้รับมอบหมายเข้าใกล้ไฟเพื่อเก็บข้อมูล เหตุจริงให้ทีมภาคสนามที่รับผิดชอบเป็นผู้กำหนดจุดและวิธีเก็บ

## 6. เป้าหมายทดลองเบื้องต้นที่เสนอให้ร่วมตกลง

นี่เป็น **เกณฑ์เสนอสำหรับ prototype** ไม่ใช่มาตรฐานที่ผ่านรับรองหรือผลที่ทำได้แล้ว:

- ผู้ทดลองอย่างน้อย 80% ทำงานอ่านสถานการณ์/แจ้ง/ติดตามที่กำหนดได้เองหลังแนะนำสั้น ๆ บันทึกทั้งจำนวนคนและจำนวนงาน ไม่รายงานเปอร์เซ็นต์โดยไม่มีตัวหาร
- ตั้งเป้าอธิบายสถานการณ์สำคัญได้ใน 60 วินาที และส่งแบบแจ้งสั้นได้ใน 2 นาทีเมื่อเน็ตพร้อม แยกเวลาเครื่อง/เครือข่ายออกจากเวลาที่คนใช้
- เหตุซ้อมหนึ่งรายการที่ retry ต้องไม่กลายเป็นเหตุใหม่ซ้ำ และการเข้าถึงข้ามสิทธิ์ต้องไม่สำเร็จในชุดกรณีที่ทดลอง
- ชื่อผู้รับประสาน สถานะ เวลา และเหตุผลต้องอยู่ครบทุกกรณีซ้อมที่ตรวจ
- ขอวัดกระบวนการเดิม เช่น โทร/LINE ควบคู่กันจากสถานการณ์ซ้อมเดียวกัน จัดลำดับทดลองสลับกันเพื่อลดผลของการฝึก ไม่บังคับเลิกเครื่องมือเดิมระหว่าง pilot
- ความแม่นยำ hotspot/การลาม/PM ยังไม่ตั้งเลขเป้าหมายจนทราบ sample, เครื่องอ้างอิง, pixel, เวลา และวิธีวัดที่หน่วยงานยอมรับ

## 7. สิ่งที่เตรียมก่อนเดินทาง

1. ตัวแทน 2 ชุมชนและผู้ดูแลสิทธิ์ที่ยืนยันได้ พร้อมรายการรหัสขอบเขตที่รับผิดชอบ
2. ระบบทดลองแยกจากเหตุจริงและบัญชีตามบทบาท การสมัคร/ยืนยันอีเมลทดสอบครบก่อนเดินทาง ไม่ใช้ admin บัญชีเดียวแทนการทดสอบหลายบทบาท
3. โทรศัพท์จริงของผู้ใช้ อุปกรณ์ทีม notebook, power bank, ซิม/สัญญาณสำรอง และเครื่องมือวัดที่ยืมได้ตามแผน ไม่ต้องซื้ออุปกรณ์ทุกอย่างเพื่อเริ่ม UX pilot
4. สถานการณ์ซ้อมเดียวกันและเกณฑ์วัด แบ่งผู้ดำเนินการกับผู้สังเกต เพื่อลดการสอนคำตอบระหว่างทดสอบ
5. แผนเก็บข้อมูล รูป และข้อมูลติดต่อ ระบุสิทธิ์เข้าถึง/การเผยแพร่และขอความยินยอมก่อนบันทึกหน้าจอหรือข้อมูลส่วนตัว
6. ผู้รับผิดชอบความปลอดภัย จุดเข้าถึง และเงื่อนไขหยุดการเก็บข้อมูลเมื่อทีมภาคสนามแจ้ง
7. ตัวอย่างรายงานเฉพาะป่า แบบบันทึก และข้อมูลเหตุย้อนหลังจากหน่วยงานพร้อม provenance ถ้ามี

### แบบบันทึกขั้นต่ำ

**การใช้เว็บ:** รหัสผู้ทดลอง, บทบาท, forest_id, งานที่ให้ทำ, อุปกรณ์/เครือข่าย, เวลาเริ่ม/จบ, สำเร็จเอง/มีคนช่วย/ไม่สำเร็จ, จุดที่สับสน, ข้อเสนอ

**หลักฐานเหตุ:** event_id, forest_id, lat/lon, GPS accuracy (m), observed_at, recorded_at, ผู้ยืนยันและที่มาระดับที่ได้รับอนุญาต, พบไฟ/ควัน/ไม่พบ/ยังตรวจไม่ได้, รูปและทิศที่ถ่าย, hotspot product/id/detection time/retrieval time, สภาพอากาศและข้อจำกัดการสังเกต

เก็บเวลาพร้อมเขตเวลา อย่าแทนเวลาเกิดเหตุด้วยเวลาส่งข้อมูลย้อนหลัง และอย่าให้รูปที่ไม่มีพิกัด EXIF ถูกตีความว่าไม่มีตำแหน่งเหตุ เพราะตำแหน่งควรอยู่ใน record แยกจากไฟล์รูป

## 8. กำหนดการตัวอย่าง

- ก่อนลงพื้นที่: นัดและยืนยันบทบาท/บัญชี/ระบบซ้อม เตรียมกรณีและข้อมูลย้อนหลัง
- วันแรก: ทบทวนงานเดิมและขอบเขตป่า → ทดสอบอ่าน/แจ้งบนมือถือ → กรณีเน็ตหลุด → สรุปปัญหากับกลุ่มแรก
- วันที่สอง: กลุ่มที่สอง → ซ้อมประสานข้ามชุมชน/อีเมล/รายงาน → สำรวจจุดอ้างอิงปลอดภัยและสรุปร่วมกับหน่วยงาน
- 7–14 วันหลังจากนั้น: ติดตามการใช้งานและปัญหา พร้อม channel สนับสนุนที่ตกลงไว้ หากเก็บข้อมูลเหตุจริงต้องมีผู้รับผิดชอบยืนยันและเงื่อนไขที่ชัดเจน
- หลัง pilot: ส่งผลเวลา/งานสำเร็จ/ข้อผิดพลาด/ข้อเสนอ พร้อมรายการแก้ไขและระบุข้อมูลที่ยังไม่พอ ไม่ประกาศ accuracy จาก sample เล็ก

## 9. สิ่งที่ควรขอข้อสรุปจากที่ประชุม

1. ใครเป็นผู้ใช้หลักใน pilot และชุมชนใดพร้อมร่วมจริง? ใครช่วยยืนยันตัวแทนและขอบเขตที่รับผิดชอบ?
2. เมื่อเห็น hotspot หรือรายงานควัน ขั้นตอนจริงคือใครตรวจ ใครรับเรื่อง ใครประสาน และเมื่อใดถือว่าปิดเหตุ?
3. งาน 3 อย่างที่ต้องทำได้ง่ายที่สุดบนโทรศัพท์คืออะไร? อีเมลเหมาะกับการแจ้งข้อมูลประเภทใดสำหรับคนหน้างาน?
4. หน่วยงานให้ข้อมูลเหตุย้อนหลัง เวลา ขอบเขต และรูปที่ใช้ตรวจสอบได้อะไรบ้าง? ส่วนไหนเผยแพร่ได้และส่วนไหนเป็นข้อมูลภายใน?
5. สนับสนุนพื้นที่ เครื่องมือ ผู้ประสาน และช่วงทดลองได้แค่ไหน? มีเงื่อนไขความปลอดภัยและการบันทึกข้อมูลอะไร?
6. ตกลงเป้าหมาย เวลา/งานสำเร็จ/การเข้าถึงข้อมูล และวิธีประเมินให้ชัด ก่อนกำหนดว่าระบบพร้อมใช้วงกว้าง

## 10. คำตอบสั้นสำหรับคำถามที่อาจถูกถาม

- **พร้อมใช้จริงหรือยัง?** พร้อมทดลองงานอ่านข้อมูลและประสานเหตุ ยังต้องตรวจบัญชี/อีเมลผู้ใช้ทั่วไปและ pilot ไม่ถือว่าโมเดลพยากรณ์ผ่านการรับรองแล้ว
- **ทำนายไฟไปไหนได้แล้วหรือยัง?** ตอนนี้มีภาพประกอบปลายลมและส่วนทดลอง ต้องเพิ่ม DEM/fuel จริงและข้อมูลอ้างอิงก่อนรายงาน accuracy
- **ทำไมไม่ใช้ LINE?** แนวทางโครงการเลือก Resend/email แต่ต้องทดลองกับคนหน้างานว่าเขาเห็นและใช้อีเมลทันหรือไม่ ถ้าไม่เหมาะต้องนำผลกลับมาหารือ ไม่ถือว่าการเลือกเทคโนโลยีตอบพฤติกรรมผู้ใช้แล้ว
- **ทำไมเว็บไม่มีรายชื่อหัวหน้าป่าครบ?** ชุดที่ได้รับยืนยันเป็นขอบเขตป่า ยังไม่มีทะเบียนผู้รับผิดชอบที่ตรวจสอบครบ ต้องขอความร่วมมือ ไม่เดาบุคคลหรืออำนาจจากแผนที่
- **กล้องสดทำแล้วหรือยัง?** ยังไม่เชื่อม live CCTV มีแหล่ง snapshot ที่พบ แต่ต้องตรวจเวลา/สิทธิ์ก่อนนำมาแสดง
- **พรุ่งนี้ควรขออะไรเป็นหลัก?** ขอคนและพื้นที่ทดลอง กระบวนการจริง และข้อมูลที่ใช้ตรวจสอบผล มากกว่าขอเพิ่มฟีเจอร์จำนวนมากโดยยังไม่รู้ว่าช่วยงานคนใช้ได้หรือไม่
